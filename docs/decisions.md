# Decisions — climbing partner app, v1

Rationale behind specs and constraints. Not input to the critic: only specs.md, constraints.md and non-goals.md cross that boundary.

- D1. Norwegian↔French grade conversion is approximate (e.g. 7- ≈ 6b/6b+). This is acceptable only because grade is a soft criterion: a conversion error can move a candidate in the list but can never exclude them (S14). If grade ever becomes a hard criterion, this decision must be revisited. The table in src/ClimbOn.Domain/Grades/RopeConversionTable.cs was accepted by the owner on 2026-10-01 as that approximation.
- D2. Distance is straight-line between postcode reference points, not travel distance or travel time. Straight-line distance is never longer than road distance, so it can only wrongly include a candidate, never wrongly exclude one. This is acceptable because S4.1 is a hard criterion, where false exclusion is the worse error. Separate imprecision: reference points are not home addresses. This error goes both ways and grows with postcode area size; it is small in Oslo and larger in rural areas.
- D3. Ended chats stay readable to both parties. The reporter needs a trail for the report; the reported party needs the same trail in case a report is unfair. Silently discarding messages to hide a block was rejected as deceptive, and because it would produce messages nobody can read or report.
- D4. The age check works on dates, not timestamps. Near midnight on the 18th birthday the check can be off by up to two hours. Accepted: the error window is tiny and the consequence is only a delayed registration. Under C3 dates are UTC dates, and Oslo is always ahead of UTC, so the error can only be a false rejection, never admission of someone under 18 in Norway.
- D5. Deletion has two phases because an immediate erasure right collides with the trail (D3): a harasser could delete the account right after a message and take the evidence with them. The 30-day deactivation keeps the trail within the one-month window for erasure requests. An email hash is still personal data (it can be reversed by hashing a list of known emails), so S41 needs a stated retention period and legal review before launch.
- D6. A deletion request pauses connections instead of ending them. Deletion may be accidental, and ending would cost the climber matches that cancelling cannot restore. Keeping them for 30 days costs almost nothing.
- D7. S46 keeps the identifier hash (S41) even when a suspended climber requests erasure. This rests on legitimate interest in preventing a suspended user from re-registering.
- D8. Card distances are rounded and have a floor of 2 km, so that several accounts cannot triangulate a climber's exact postcode. This limits the risk rather than eliminating it; postcode-level location remains inferable. Metadata is stripped from photos because phone photos can carry GPS coordinates, which would reveal more than the postcode does.
- D9. The ordering is lexicographic, not a weighted score. There is no data to set weights from, and every position in the list must be explainable by a single key. Window overlap is the first key because time is the scarce resource the app exists to save. Gear is not an ordering key: indoors it can be rented, outdoors the pair agrees on it in chat, and ranking by it would mostly push newcomers down.
- D10. The client is a PWA: one codebase, no app-store review or fees, deployed like a website. iOS delivers web push only to home-screen-installed web apps, so email is the only channel guaranteed to reach every climber.
- D11. Modular monolith: the expected load does not justify distribution. Module boundaries are drawn so a module could be split out later; the load at which that would pay off is recorded when it becomes relevant. PostgreSQL over SQL Server because its container starts in seconds, which is paid on every CI run (C11). Preferred region is Norway East; the constraint itself is EEA (C13), so another EEA region is acceptable if a required service is unavailable there.
- D12. Traceability is a set difference computed by CI (C17), not a judgement. But a test that asserts nothing would satisfy C17, so mutation testing (C18) is what shows the tests can fail. Remaining gap: C18 covers only the domain module, so a vacuous integration test tagged with an S-ID still passes C17. Accepted for v1; recorded so it is not mistaken for full coverage.
- D13. Terraform over Bicep: cloud-agnostic. Account IDs in telemetry are pseudonymous; after erasure (S38) nothing maps them to a person, and the telemetry itself expires within 30 days (C31).
- D14. Erasure reaches backups by expiry (7 days), not by editing backups. The replay log keeps entries for twice the backup retention: long enough for any restore point, short enough that it never becomes a permanent list of erased accounts. Replay re-applies only the actions recorded in the replay log. All other writes made after the restore point are lost, regardless of who made them.
- D15. Password login instead of login links: a link at every session renewal forces a switch to the inbox. Breached-password checks are deferred (L4). Lockout (S81) lets anyone who knows a climber's email keep that account locked by repeated failed attempts. Accepted at v1 scale; revisit together with L4.
- D16. The login method is fixed at registration, so that no flow can change it as a side effect. The earlier version of S85 covered only collisions with password accounts; the same Gmail address used through both Google and Facebook would have created two accounts, or undefined behaviour under S84.
- D17. The reported climber learns of a report only when an action is taken, never when it is filed. In a small local network the reporter is often inferable from recent interactions, and a notice at filing time would expose them to someone who knows their gyms and schedule. The admin controls timing through when the report is closed. A warning before suspension is optional; threats or fake profiles warrant immediate suspension.
- D18. Every email goes to an address that belongs to an account, so every email uses the account's language. The case "email to an address without an account" does not occur: S80.2 sends nothing then.
- D19. Blazor WebAssembly keeps the whole solution in one language (C#). Accepted costs: a larger first download (the .NET runtime is downloaded once, then cached), and push handling in hand-written JavaScript because Blazor has no built-in support for it.
- D20. Managed identity removes the database secret; OIDC federation removes the CI secret. Push protection and a CI scan are both used because push protection recognises only known secret formats. Regenerating the Apple secret monthly means one failed run leaves five months of warnings before Apple login stops working.
- D21. Target is WCAG 2.1 AA because it includes all 2.0 criteria, covering Norwegian requirements whichever version applies. Automated scans find only a minority of failures, so C61 is required; a passing scan shows that certain errors are absent, not that the client conforms.
- D22. The admin is a separate Entra identity with MFA because it can suspend anyone and read report attachments. A password with lockout would give the strongest account the weakest protection. A separate hostname keeps admin code out of the climber download and isolates browser storage. A person who is both admin and climber uses two identities. The admin client is outside WCAG scope because its only user is known.
- D23. Dormant accounts are deleted through the ordinary deletion path (S37–S39) rather than a separate one: one erasure path to test, and the other party keeps the 30-day reporting window (D5). Periods are counted in days, not calendar months, so the rules are exact under the injectable clock (C4).
- D24. The legal basis for core processing (profile, matching, invites, chat, notifications) is performance of a contract, not consent: consent can be withdrawn, and the service cannot run without this data. The privacy policy is therefore acknowledged, not accepted.
- D25. Email moved from Azure Communication Services to Scaleway Transactional Email (2026-10-06): Microsoft is retiring ACS Email (2028-09-30) and closes it to new customers from 2026-10-23, before this subscription would have created a resource. Scaleway is EU-owned with processing in France (C13, C14) and is free at v1 volumes. Its cost sits outside Azure, so C15 names it and gives it its own alert. Unlike ACS there is no shared sender domain, so a domain is bought in M1 rather than before M2. The adapter speaks plain SMTP so that a further provider change touches configuration and Key Vault, not code. No CI credential for Scaleway exists, because it has no OIDC federation; the cost is that the Scaleway Terraform is applied by the owner and is outside the drift check.

## Legal review before launch

- Retention periods and the identifier hash as personal data (D5, S41).
- Hash retention overriding an erasure request from a suspended climber (D7, S46).
- Withholding reports about the climber from an access request (S64).
- Web push delivery metadata passing through non-EEA push services (C13 exception).
- Scaleway's DPA and EEA-only processing for Transactional Email (C13, C14).
- Digital Services Act: statement of reasons to affected users (S93), and whether and how it applies in Norway at this scale.
- Whether Norwegian universal-design rules apply to a private, non-commercial app (C59).
- The terms and privacy policy texts, and confirmation that no special-category data is processed (D24).
